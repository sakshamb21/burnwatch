# UI ↔ Backend Integration Change Log

This log records real gaps found while implementing the five dashboard UI. None of these items are silently emulated as a production feature.

| Feature / issue | Why it is needed | UI behaviour today | Required backend / infrastructure change | Security implications | Status | Acceptance criteria | Production blocker |
|---|---|---|---|---|---|---|---|
| Authentication and sessions | Administrator Operations and case actions require identity. | Five dashboards are public; administrator sign-in is in-memory visual state only. | Identity provider/session/token verification; `401`/`403`; server middleware. | Prevents unauthenticated administration. | BLOCKED | Every protected request validates identity. | Yes |
| Role and resource authorization | Roles need least-privilege enforcement. | UI only hides/disables administrator options. | Role/resource permissions on each endpoint and audit logs. | Frontend guards are bypassable. | BLOCKED | Public user cannot mutate; protected records enforce scope. | Yes |
| Source-mode switching | Operations requests explicit simulated/live control. | Shows configured mode; explains restart/configuration requirement; cannot switch. | Authorized status + change endpoint or managed deployment config with audit trail. | Must not let browser change operational source without permission. | BLOCKED | Switch is authorized, auditable, truthful, and never silently falls back. | Yes |
| Live telemetry health/freshness | Operators must know whether hardware is connected. | “Hardware interface not configured” unless API supplies data. | Ground-station adapter + `/telemetry/status` endpoint implemented. | Serial remains backend-only. | DONE | State includes connected/disconnected/configured and last packet time. | No |
| Serial integration | Hardware is not browser-accessible. | No serial commands or port paths in UI. | Isolated server/ground-station service via `CanSatLiveSource` & `burnwatch live`. | Prevents arbitrary hardware control. | DONE | Authorized, audited, validated operations only. | No |
| Community-report retrieval | Map/workflow need real report list/detail. | POST is supported; acknowledged reports are current-session only. | `GET /reports`, `GET /reports/{id}`, pagination/filtering and report status. | Must restrict private contact data. | BLOCKED | Authorized views receive only permitted fields. | Yes |
| Report event date/time, address, photos | Product form requires them. | Clearly marked unavailable; not faked. | Schema fields, upload flow/object storage, validation, retention policy. | Personal/sensitive content needs controls. | BLOCKED | Upload acknowledgement/progress/failure and safe access rules. | Yes |
| Report-to-case links and moderation | Prevents allegations becoming verified automatically. | Separate visual categories only. | Explicit association/review endpoints and audit history. | Avoids unreviewed allegations being published as facts. | BLOCKED | Link requires authorized server action and records actor/reason. | Yes |
| Canonical operational statuses | Required workflow uses more stages than backend model. | Shows backend statuses without unsafe relabeling. | Add/define reported, inspection-requested/completed, action, closure fields/transitions. | Transitions need role rules and audit. | BLOCKED | Mapping is explicit, valid transitions enforced server-side. | Yes |
| Assignment, due dates, next actions | Investigation coordination. | Marked unavailable. | Case assignment/action fields and permissioned update endpoints. | Data visibility and write scopes. | BLOCKED | Authorized assignments, validation, audit history. | No, but required for requested workflow depth |
| Incident evidence query | Event Evidence needs exact associated observations. | Filters available observations by device; labels relationship limitation. | Endpoint to list observations for incident, ordered/paginated. | Evidence access may need restrictions. | TODO | Exact evidence set available without client inference. | No |
| Impact aggregations | Reliable metrics/trends need server definitions. | Client computes only explicit, labeled local aggregates; unsupported metrics unavailable. | Aggregation endpoint with date range, provenance and metric definitions. | Aggregates must not leak restricted data. | TODO | Candidate/confirmed/reports/inspections stay distinct. | No |
| Map hosting/geocoding | A production map may need cartography/address search. | Uses Leaflet with public OpenStreetMap tiles, visible attribution, and no prefetch/offline cache. | Production map-hosting decision, geocoding, terms/privacy and scaling review. | Avoid unrestricted keys and misuse of shared public tiles. | TODO | Provider policy, attribution, traffic limits, and fallback behaviour are documented and tested. | No |
| Rate limiting and abuse protection | Public reports can be abused. | UI validates input only. | Rate limit, CAPTCHA/trusted mechanism, payload limit, moderation. | Public endpoint abuse/DoS/privacy risk. | BLOCKED | Tests cover limits and malformed/oversized input. | Yes |
| Current raw payload preservation | Chain of evidence requires original packets. | UI never claims raw packet access. | Pass/persist raw payload in API/replay ingestion path; expose authorized evidence view if appropriate. | Raw data access needs policy. | TODO | Stored original can be traced to normalized observation. | Yes for evidentiary deployment |
